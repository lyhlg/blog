# 블로그 포스트 작성 스킬

사용자가 제공한 컨텐츠/주제를 바탕으로, 기존 블로그 스타일과 인기 콘텐츠 패턴을 반영한 MDX 포스트를 작성한다.

## 입력

- 전체 인자: `$ARGUMENTS`

## 0단계: 입력 파싱

`$ARGUMENTS`에서 카테고리와 주제/내용을 파싱한다.

- `tech <주제/내용>` → 기술 포스트
- `diary <주제/내용>` → 일기 포스트
- `retrospective <주제/내용>` → 회고 포스트
- 카테고리 없이 내용만 있으면 → 내용을 분석해서 적절한 카테고리를 추천하고 사용자에게 확인

## 1단계: 컨텐츠 수집 (인터랙티브)

사용자가 제공한 내용을 분석하고, 부족한 정보를 질문으로 수집한다.

### 필수 수집 항목

AskUserQuestion을 사용하여 다음을 확인한다. 이미 인자에 포함된 항목은 건너뛴다.

1. **핵심 내용**: 어떤 내용을 다루는 포스트인지 (이미 제공됐으면 스킵)
2. **대상 독자**: 누가 읽을 글인지 (주니어 개발자, 시니어, 비개발자 등)
3. **글의 목적**: 문제 해결 공유 / 지식 전달 / 경험 공유 / 의견 제시

### 선택 수집 항목

필요한 경우에만 추가로 질문한다:

- **스크린샷/이미지**: "이 부분에 대한 스크린샷이나 참고 이미지가 있나요?"
- **코드 예시**: "실제 코드나 설정 파일이 있다면 공유해주세요"
- **참고 자료**: "관련 링크나 문서가 있나요?"
- **특별히 강조하고 싶은 포인트**: 사용자가 반드시 전달하고 싶은 핵심 메시지

수집 시 한 번에 2-3개 이하의 질문만 한다. 질문이 많으면 나눠서 물어본다.

## 2단계: 리서치 (tech 카테고리일 때)

기술 포스트인 경우 WebSearch를 사용하여 보충 자료를 수집한다.

- 주제와 관련된 공식 문서나 레퍼런스 확인
- 유사한 문제/주제를 다룬 인기 글이 있는지 확인 (차별점 파악용)
- 참고 자료 섹션에 넣을 링크 수집

리서치 결과를 간략히 사용자에게 공유하고, 방향성을 확인받는다.

## 3단계: 아웃라인 작성

포스트 아웃라인을 작성하여 사용자에게 보여주고 승인을 받는다.

아웃라인에는 다음이 포함된다:
- 제목 (안)
- 간단 설명 (description)
- 태그 후보
- 섹션 구성 (각 섹션에 들어갈 핵심 내용 1-2줄)
- 예상 코드 블록, 다이어그램 위치

**중요**: 사용자가 아웃라인을 승인하거나 수정 요청을 할 때까지 본문 작성에 들어가지 않는다.

## 4단계: 본문 작성

승인된 아웃라인을 바탕으로 MDX 포스트를 작성한다.

### 4-1. frontmatter

```yaml
---
title: "{제목}"
description: "{1줄 설명 - 호기심 유발하는 문장}"
date: "{오늘 날짜 YYYY-MM-DD}"
category: "{tech|diary|retrospective}"
tags: ["{태그1}", "{태그2}", ...]
draft: true
---
```

### 4-2. 글쓰기 원칙

다음 원칙을 **반드시** 따른다:

#### 가독성
- 한 문장은 **40자 이내**를 목표로 한다. 길어지면 끊는다
- 한 문단은 **3-4줄 이내**. 빽빽한 글은 읽히지 않는다
- 전문 용어를 처음 사용할 때는 간단히 설명을 붙인다
- 불필요한 수식어를 제거한다. "매우", "정말", "상당히" 같은 표현을 최소화한다

#### 톤 & 스타일
- 경어체 사용 ("~합니다", "~입니다")
- 딱딱한 논문체가 아닌, **대화하듯 자연스러운 톤**
- 기존 블로그의 톤 참고: 핵심을 직접적으로 전달하되, 경험을 곁들인 설명
- 이모지는 정리/요약 섹션에서만 제한적으로 사용 (남용 금지)

#### 인게이지먼트 구조
- **서두 훅**: 첫 2-3줄 안에 독자의 관심을 잡는다
  - 패턴 A (문제 제시): "PR을 올렸는데 CI에서 에러가 터졌습니다"
  - 패턴 B (질문형): "모노레포에서 lockfile이 깨지는 이유, 알고 계셨나요?"
  - 패턴 C (결론 먼저): "결론부터 말하면, peerDependencies가 원인이었습니다"
- **TLDR 블록**: 서두 훅 직후, 핵심 내용을 3-5줄로 요약
  - "---" 구분선으로 감싸서 시각적으로 분리
  - 바쁜 독자가 여기만 읽어도 핵심을 파악할 수 있도록
- **중간 연결**: 섹션 전환 시 다음 내용에 대한 기대를 만든다
  - "그렇다면 왜 이런 일이 벌어질까요?"
  - "해결법을 찾기 전에, 먼저 배경을 이해해야 합니다"
- **마무리**: 핵심 요약 + 독자에게 남기는 한마디

### 4-3. 카테고리별 구조

#### tech (기술 포스트)

```
서두 훅 (문제 상황 또는 핵심 질문)

---

## TLDR
> 핵심 내용 3-5줄 요약. 바쁜 독자를 위한 섹션.

---

## 문제 상황 (또는 배경)
- 어떤 상황에서 이 문제/주제를 만났는지
- 코드 블록이나 에러 메시지 포함

## 원인 분석 (또는 핵심 개념)
- 문제의 원인 또는 주제의 핵심 개념
- Mermaid 다이어그램으로 시각화 (적합한 경우)
- 코드 예시로 설명

## 해결 방법 (또는 적용 방법)
- 구체적인 해결책 또는 적용 방법
- diff 블록으로 변경 전/후 비교
- 여러 방법이 있다면 장단점 비교

## 추가 고려사항 (선택)
- 트레이드오프, 주의사항

## 정리
- 핵심 포인트 번호 목록
- 이모지 활용 가능 (✅, ❌ 등)

## 참고 자료
- 관련 공식 문서, 블로그 링크

---

마무리 한마디 (자연스러운 클로징)
```

#### diary (일기)

```
자연스러운 도입 (그날의 상황/감정)

## 소제목들로 이야기 전개
- 자유로운 구성
- 개인적 감정과 생각 포함
- 짧고 임팩트 있는 문장

마무리 (배운 점이나 느낀 점)
```

#### retrospective (회고)

```
서두 (어떤 기간/경험에 대한 회고인지)

---

## TLDR
> 회고의 핵심 인사이트 요약

---

## 배경 / 타임라인
## 잘한 점
## 아쉬운 점
## 배운 점
## 앞으로의 계획

---

마무리
```

### 4-4. 코드 블록 & 다이어그램

- 코드 블록: 언어 태그를 반드시 지정 (```bash, ```typescript 등)
- diff 블록: 변경 전후를 보여줄 때 ```diff 사용
- Mermaid 다이어그램: 프로세스 흐름이나 구조를 설명할 때 적극 활용
  ```mermaid
  flowchart LR
      A[시작] --> B[과정]
      B --> C[결과]
  ```
- 인라인 코드: 명령어나 변수명은 `backtick`으로 감싼다

### 4-5. 이미지/스크린샷

사용자에게 스크린샷이 필요한 위치를 안내하고, 업로드를 요청한다.
이미지 플레이스홀더를 마크다운으로 남긴다:

```markdown
![설명 텍스트](/images/posts/{slug}/{파일명})
```

## 5단계: 리뷰 & 저장

### 5-1. 미리보기 제공

작성된 포스트 전문을 사용자에게 보여주고 피드백을 받는다.

수정 요청이 있으면 반영한다. 특히 다음을 확인한다:
- 톤이 적절한지
- 기술적 내용이 정확한지
- 빠진 내용이 없는지
- 너무 길거나 짧지 않은지

### 5-2. 파일 저장

사용자 승인 후:

1. 파일명 결정:
   - 한국어 제목을 slug로 변환 (공백 → 하이픈, 특수문자 제거)
   - 또는 사용자가 원하는 slug 사용
2. 저장 경로: `content/posts/{category}/{slug}.mdx`
3. Write 도구로 파일 저장
4. `draft: true` 상태로 저장 (사용자가 직접 false로 변경)

### 5-3. 결과 보고

저장 완료 후 다음을 알린다:
- 저장 경로
- 제목과 설명
- 태그 목록
- `draft: true` 상태임을 안내하고, 발행 시 `false`로 변경하라고 알림
- 이미지 플레이스홀더가 있다면 업로드 필요 안내

## 글쓰기 체크리스트 (내부 검증용)

포스트 작성 완료 후, 아래 항목을 스스로 점검한다:

- [ ] 서두 3줄 안에 독자의 관심을 끄는 훅이 있는가?
- [ ] TLDR이 포함되어 있는가? (diary 제외)
- [ ] 한 문장이 40자를 크게 넘지 않는가?
- [ ] 한 문단이 4줄을 넘지 않는가?
- [ ] 전문 용어에 설명이 붙어 있는가?
- [ ] 코드 블록에 언어 태그가 있는가?
- [ ] 섹션 전환이 자연스러운가?
- [ ] 마무리가 있는가?
- [ ] frontmatter가 올바른 형식인가?
- [ ] 이모지를 남용하지 않았는가?
